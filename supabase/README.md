# Supabase migrations — the schema's single source of truth (ADR-0008)

This directory holds the database schema's source of truth: one ordered set of
SQL files applied by **one runner in every environment**.

## One history, one runner

The schema is applied by the project-owned runner (ADR-0008) — not the Supabase
CLI, not Drizzle's migrator:

```bash
pnpm db:migrate   # apply pending migrations (uses MIGRATION_DATABASE_URL)
pnpm db:status    # what the database has applied vs what HEAD ships
pnpm db:check     # exit 1 unless the database exactly matches HEAD (CI gate)
pnpm db:migrate:new <slug>   # scaffold the next file
pnpm db:reset     # DEV ONLY: drop and re-apply everything
```

The same runner applies the same files in CI's `test-db` job and in the deploy
pipeline's migrate-before-deploy step (the API image ships its own copy of this
directory). One ledger (`ses_meta.migrations`) answers "what does this database
believe?" everywhere.

The runner needs only a Postgres owner URL — no vendor CLI, no linked project.
The history is self-sufficient on stock Postgres (the first migration creates
the roles, the `auth` shim and the grants the policies assume; on hosted
Supabase those statements skip themselves). See ADR-0008 for the decision and
the alternatives that were rejected.

## Naming

`<UTC timestamp>_<subject>.sql` (14-digit UTC timestamp, lowercase subject) —
generated by `pnpm db:migrate:new`, never typed by hand. Files sort in apply
order.

## Immutability

**An applied migration is immutable — the runner's checksum ledger enforces
it.** Editing a file after it has been applied makes the next run fail with a
checksum mismatch, by design: the database no longer matches the repository.
Fix forward with a new migration (see `20260923162920_society_gen_join_code_grant.sql`
for the pattern, added after the RLS canary caught the original bug). Deleting
or renaming an applied file is likewise fatal.

Every migration carries a commented `down` block documenting the reverse
operation. The runner is forward-only; the `down` is applied by hand when a
release must be reverted.

## Manual fallback (no toolchain available)

Without pnpm or the repo, paste each file's contents into
**Dashboard → SQL Editor** in filename order. The SQL is idempotent, so
re-running is safe — but the `ses_meta` ledger will not be written, so the next
`db:check` will report the database behind and the missing files must then be
recorded by running `pnpm db:migrate` once against the same database (it will
re-execute nothing already applied by hand only if the SQL is idempotent AND
the checksums are then inserted — the runner records rows for files whose
statements were no-ops). Prefer the runner in every case.

## `supabase db push` (legacy instructions)

The Supabase CLI can still apply these files (`npx supabase login &&
npx supabase link --project-ref <ref> && npx supabase db push`). It is no
longer the documented path — it writes Supabase's own ledger rather than
`ses_meta`, which desynchronises the gate every other environment trusts. If
you must use it, run `pnpm db:migrate` afterwards to reconcile the ledger.
